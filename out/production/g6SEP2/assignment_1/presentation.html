📋 Project Overview

The Vinyl Library is a JavaFX desktop application that simulates a physical vinyl record lending library. A librarian can see all records, check their availability, and perform actions like borrow, reserve, return, and remove. At the same time, two background threads (Bob and Wendy) simulate real users autonomously performing random actions on the vinyls to stress-test the concurrent behaviour.

What the app does

🗂️ Vinyl Catalogue

Displays 10 pre-loaded classic vinyl records (Thriller, Abbey Road, The Wall…) in a sortable table with title, artist, year, and live status.

⚙️ Manage Screen

Selecting a vinyl and clicking Manage opens a detail view where the librarian can borrow, reserve, return, or remove the record.

🤖 User Simulators

Two background threads (Bob & Wendy) randomly pick a vinyl every 2–5 seconds and attempt a random action, simulating concurrent library users.

🔄 Live Updates

Any state change — whether from a button click or a background thread — is immediately reflected in the front table via the Observer pattern.

🏗️ Architecture – MVVM

The project follows the Model–View–ViewModel (MVVM) architectural pattern. MVVM separates business logic from UI code, making each layer independently testable and replaceable.

🖥️ View FrontController, ManageController, Front.fxml, Manage.fxml, ViewHandler — Only deals with displaying data and capturing user input. Never talks to the Model directly.
🔗 ViewModel FrontVM, ManageVM, ViewState — Bridges View and Model. Holds UI-ready data, exposes JavaFX StringProperty bindings, translates user actions into Model calls, and listens to Model events via ModelListener.
🗄️ Model ModelManager, Vinyl, VinylList, all State classes — Pure business logic. Knows nothing about JavaFX or the UI. Manages the vinyl collection, enforces state transitions, and fires events.

Dependencies only point inward. The Model never imports anything from the View or ViewModel. This means you could swap the entire UI (e.g. switch from JavaFX to Swing) without touching the model package.

🗄️ Model Layer — Deep Dive

Model interface

Model.java is a Java interface that defines the entire public API of the data layer. Everything that any other layer is allowed to call on the model goes through here. Using an interface means the ViewModel and View are never coupled to the concrete implementation — you could replace ModelManager with a database-backed version without changing a single line elsewhere. 

public interface Model {
  // Observer registration
  void addListener(ModelListener listener);
  void removeListener(ModelListener listener);

  // CRUD
  void addVinyl(String title, String artist, String year);
  void removeVinyl(Vinyl vinyl);
  List<Vinyl> getVinylList();
  Vinyl getVinylByIndex(int index);

  // Domain actions
  void reserve(Vinyl vinyl, String userName) throws IllegalStateException;
  void borrow(Vinyl vinyl, String userName)  throws IllegalStateException;
  void returnVinyl(Vinyl vinyl)                throws IllegalStateException;
}

ModelManager — the concrete implementation

ModelManager holds the canonical list of Vinyl objects and a list of registered ModelListeners. Every mutating action follows the same three-step pattern:

1. Acquire lock
(synchronized)
→
2. Mutate state
(delegate to Vinyl)
→
3. Notify listeners
(fire event)

Smart removal — the "marked for removal" flag

You cannot physically delete a vinyl that is currently borrowed or reserved — someone is using it. The project solves this with a deferred removal strategy:

  • If the vinyl is Available → remove it immediately from the list.
  • Otherwise → set markedForRemoval = true and fire a vinylMarkedForRemoval event.
  • When returnVinyl() is later called and the state transitions back to Available, the ModelManager checks the flag and performs the actual removal automatically.
This guarantees that a vinyl is never pulled from the library while someone has it, and no manual cleanup is ever needed.

Vinyl — the domain entity

Vinyl is the central domain object. It is Serializable (prepared for persistence) and holds:

FieldTypePurpose
title, artist, yearStringDescriptive metadata
stateStateCurrent lifecycle state (State Pattern object)
markedForRemovalbooleanDeferred deletion flag
reserveNameStringName of the person who has reserved the vinyl
borrowNameStringName of the person who has borrowed the vinyl

The four action methods (borrowVinyl, reserveVinyl, returnVinyl, removeVinyl) are all synchronized and simply delegate to the current State object — this is the State Pattern in action.

VinylList — the observable collection

VinylList is a wrapper around ArrayList<Vinyl> that adds a PropertyChangeSupport bus. Every mutation (add, remove, borrow, reserve, return) fires a named property-change event. This is the older / alternative observer mechanism used when the project was partially built; the main flow now uses ModelListener instead.

⚠️ VinylList and ModelManager maintain separate vinyl collections. VinylList is populated in StartApplication.initializeVinylCollection() but the main runtime operations go through ModelManager. VinylList is passed to ViewHandler but is not the live data source for the table — FrontVM reads from ModelManager. This is a mild architectural inconsistency in the current codebase.

🔀 State Pattern — The Vinyl Lifecycle

The project uses the classic GoF State Pattern to model what a vinyl record can and cannot do at any point in time. Instead of a giant if/else chain checking a status enum, each state is its own class that knows exactly which transitions are legal.

The five states

Available
Borrowed
Reserved
Borrowed & Reserved
Removed

Transition table

Each cell shows the resulting state. Empty means the action is silently ignored (no-op defined in the base class).

Current State borrow() reserve() return() remove()
Available → Borrowed → Reserved — (no-op) → Removed
Borrowed — (no-op) → Borrowed & Reserved → Available — (no-op)
Reserved → Borrowed — (no-op) — (no-op) — (no-op)
Borrowed & Reserved — (no-op) — (no-op) → Reserved — (no-op)
Removed — (terminal) — (terminal) — (terminal) — (terminal)

Why is this pattern used?

✅ Open/Closed Principle

Adding a new state (e.g. "OnLoan") means creating one new class — no existing code changes.

✅ Eliminates conditionals

No if (state == BORROWED && action == RESERVE) chains. Logic lives in the state class itself.

✅ Safe no-ops

The abstract base class State defines all 4 transitions as empty methods. States only override what they allow.

How the base class enables safe no-ops

public abstract class State {
  public void toReturn(Vinyl vinyl)  { /* do nothing */ }
  public void toReserve(Vinyl vinyl) { /* do nothing */ }
  public void toRemove(Vinyl vinyl)  { /* do nothing */ }
  public void toBorrow(Vinyl vinyl)  { /* do nothing */ }
  public abstract String getStateName();
  public abstract String status();
}

Reserved state carries its own data

Reserved and BorrowedAndReserved store the name of the person who made the reservation as a private field inside the state object itself. This is important: when a BorrowedAndReserved vinyl is returned, the state transitions to Reserved(reservedBy) — the reservation is preserved automatically because it travels with the state object. 

public class BorrowedAndReserved extends State {
  private String reservedBy;

  public void toReturn(Vinyl vinyl) {
    vinyl.setState(new Reserved(reservedBy)); // reservation is preserved!
  }
}

👁️ Observer Pattern

The project uses two complementary implementations of the Observer Pattern to propagate changes between layers.

1. ModelListener (custom interface)

This is the primary Observer mechanism between Model and ViewModel. ModelListener is a simple Java interface with four event methods: 

public interface ModelListener {
  void vinylAdded(Vinyl vinyl);
  void vinylRemoved(Vinyl vinyl);
  void vinylUpdated(Vinyl vinyl);
  void vinylMarkedForRemoval(Vinyl vinyl);
}

Both FrontVM and ManageVM implement ModelListener and register themselves with ModelManager during construction (model.addListener(this)). Whenever the model changes, ModelManager loops through all registered listeners and calls the appropriate method. This is the classic push notification model.

2. PropertyChangeSupport (Java beans)

VinylList, FrontVM, ManageVM, and ViewState use Java's built-in PropertyChangeSupport to fire named property-change events. FrontVM fires a "vinylList" event every time its list refreshes. Consumers can subscribe to specific property names, making the coupling very fine-grained.

Full notification chain

Example: Bob borrows a vinyl on a background thread
1. UserSimulator.performRandomAction() calls model.borrow(vinyl, "Bob")
↓
2. ModelManager.borrow() acquires lock on vinyl, calls vinyl.borrowVinyl(), then notifyListenersVinylUpdated(vinyl)
↓
3. FrontVM.vinylUpdated() is called (on the background thread)
↓
4. Platform.runLater(() -> refreshVinylList()) marshals back onto the JavaFX UI thread
↓
5. refreshVinylList() re-fetches the list from ModelManager and fires "vinylList" PropertyChange
↓
6. FrontController (if subscribed) calls vinylTable.refresh() — the table updates on screen
Platform.runLater() is critical: JavaFX is single-threaded and all UI mutations must happen on the JavaFX Application Thread. Background threads (Bob, Wendy) call the model directly, so the bridge back to the UI thread is mandatory.

🔗 ViewModel Layer

FrontVM

FrontVM is the main ViewModel. It implements ModelListener so it reacts to model events, and it exposes data to the View through a plain List<Vinyl> and a JavaFX StringProperty for error messages.

MemberWhat it does
modelReference to the Model interface — used to call domain actions
viewStateShared selection state (which vinyl is selected)
vinylListLocal cached copy of the model's list, kept in sync by refreshVinylList()
errorLabelJavaFX StringProperty — can be bound directly to a Label in FXML
supportPropertyChangeSupport bus for notifying the View of list updates

The ViewModel acts as a safety net for exceptions: reserveVinyl(), borrowVinyl(), and returnVinyl() all catch IllegalStateException from the model and write a friendly message to errorLabel instead of crashing.

ManageVM

ManageVM has an identical structure to FrontVM. It was created for the Manage screen but is not wired up in the current version of the UI (ManageController currently calls State methods directly on Vinyl). It exists as infrastructure for a more complete ViewModel-driven manage screen.

ViewState

ViewState is a simple shared object that holds the currently selected Vinyl. It uses PropertyChangeSupport so any component can listen for selection changes. This solves the problem of passing selection data between two different views (Front → Manage) without them directly depending on each other. 

public class ViewState {
  private Vinyl selectedVinyl;
  private PropertyChangeSupport support;

  public void setSelectedVinyl(Vinyl vinyl) {
    Vinyl old = this.selectedVinyl;
    this.selectedVinyl = vinyl;
    support.firePropertyChange("selectedVinyl", old, vinyl);
  }
}

🖥️ View Layer

ViewHandler — Scene Switcher

JavaFX uses a single Stage (window). ViewHandler is the object that owns the stage and controls which Scene is displayed. Both FXML files are loaded once at startup (loadFrontView() and loadManageView()) and their controllers are stored. Switching views is just primaryStage.setScene(scene) — fast and with no re-parsing of FXML. 

public void openManageView(Vinyl selectedVinyl) {
  manageController.setSelectedVinyl(selectedVinyl); // pass data
  primaryStage.setTitle("Vinyl Management");
  primaryStage.setScene(manageController.getScene());
  primaryStage.show();
}

FrontController — The Table View

FrontController controls Front.fxml. The FXML defines a TableView<Vinyl> with four columns: Title, Artist, Year, and Status.

The columns use JavaFX's PropertyValueFactory, which uses reflection to call the matching getter on each Vinyl object: 

titleColumn.setCellValueFactory(new PropertyValueFactory<>("title"));   // calls getTitle()
artistColumn.setCellValueFactory(new PropertyValueFactory<>("artist"));  // calls getArtist()
statusColumn.setCellValueFactory(new PropertyValueFactory<>("state"));   // calls getState() → State.toString()

The "state" column maps to getState(), which returns a State object. JavaFX calls .toString() on it, which calls getStateName() — so the display text comes directly from the State Pattern.

updateVinylTable() calls vinylTable.refresh(), forcing JavaFX to re-read all cell values. This is called every time openFrontView() is triggered, ensuring the table is always up to date when you navigate back.

ManageController — The Detail Form

ManageController controls Manage.fxml. When a vinyl is passed to it via setSelectedVinyl(), it populates four text fields with the vinyl's data. The five action buttons (Borrow, Reserve, Return, Remove, Cancel) call the corresponding state-transition methods directly on the selected Vinyl object and then refresh the UI.

⚡ Threading & Concurrency

This is one of the most important and interesting aspects of the project. Three threads run simultaneously, all touching the same shared data.

🖥️ JavaFX App Thread

The main UI thread. Handles all button clicks, renders the table, responds to user input. Must never be blocked by long operations.

🤖 Bob (UserSimulator)

Daemon thread. Sleeps 2–5 seconds, picks a random vinyl, attempts a random action (reserve/borrow/return). Ignores removed vinyls.

🤖 Wendy (UserSimulator)

Identical to Bob's thread. Runs concurrently. Bob and Wendy can both try to borrow the same vinyl at the same time.

How thread safety is achieved

The project uses Java's intrinsic synchronized keyword in two key places:

🔒 synchronized(vinylList)

All reads and writes to the List<Vinyl> in ModelManager are synchronized on the list itself. This prevents concurrent modification exceptions when Bob adds/removes while the UI reads.

🔒 synchronized(vinyl)

Each individual vinyl action (borrow, reserve, return) in ModelManager synchronizes on the specific Vinyl object. If Bob and Wendy both try to borrow the same vinyl simultaneously, one will wait for the other to finish.

🔒 synchronized methods on Vinyl

The action methods on Vinyl itself (borrowVinyl, reserveVinyl, etc.) are also synchronized, providing a second layer of protection.

The Platform.runLater() bridge

JavaFX enforces that all UI updates happen on the JavaFX Application Thread. When Bob (background thread) triggers a model change, the model calls the listener (FrontVM) on Bob's thread. FrontVM wraps its UI update in Platform.runLater(), which queues the work onto the JavaFX thread: 

// Called on Bob's background thread:
@Override public void vinylUpdated(Vinyl vinyl) {
  Platform.runLater(this::refreshVinylList); // safely handed off to the UI thread
}

Daemon threads

Both UserSimulator threads are set as daemon threads: 

thread.setDaemon(true);

A daemon thread does not prevent the JVM from shutting down. When the user closes the JavaFX window, the JVM exits and the daemon threads are killed automatically. The Application.stop() method also explicitly calls simulator.stop() which sets running = false and calls thread.interrupt() for a clean, cooperative shutdown.

⚠️ Potential race condition: ModelManager.notifyListeners*() is called outside the synchronized block in some cases. This means a listener could be notified while another thread modifies the list. This is a subtle but real threading concern in the current implementation.

Bob's Thread

↓ model.borrow(vinyl, "Bob")
2. ModelManager.borrow() — acquires synchronized(vinyl) lock
↓ vinyl.borrowVinyl() → state = new Borrowed()
3. notifyListenersVinylUpdated(vinyl) calls all listeners on Bob's thread
↓
Handed to UI Thread via Platform.runLater()
4. FrontVM.refreshVinylList() re-fetches list from ModelManager
↓ fires "vinylList" PropertyChange

Scenario C: Remove a currently-borrowed vinyl

1. ModelManager.removeVinyl(vinyl) is called
↓ vinyl.getState() is Borrowed (not Available)
2. vinyl.markForRemoval() sets flag = true; vinylMarkedForRemoval event fires
↓ vinyl stays in the list, state remains Borrowed
3. Later, model.returnVinyl(vinyl) is called by the borrower
↓ Borrowed.toReturn() → vinyl.setState(new Available())
4. ModelManager checks: isMarkedForRemoval() && state instanceof Available → TRUE
↓
5. vinylList.remove(vinyl) + notifyListenersVinylRemoved(vinyl) — vinyl disappears from table

💡 Design Decisions — The Why

🎯 Why MVVM and not MVC?

MVVM keeps the View as dumb as possible. The ViewModel exposes bindable properties so the View never needs to know how data is fetched — it just observes. This is especially natural in JavaFX which was designed around data binding.

🎯 Why an interface for Model?

Model.java is an interface so the ViewModel depends on an abstraction, not a concrete class. The real implementation (ModelManager) could be swapped for a mock in tests or a network-backed version in production.

🎯 Why the State Pattern?

A vinyl has 5 states and 4 actions = 20 combinations. Without the pattern, you'd need 20 conditional branches. With it, each state class only handles its 1–2 valid transitions and ignores the rest via the base class.

🎯 Why synchronized on vinyl objects?

Using fine-grained locks (one per vinyl) allows two threads to act on different vinyls simultaneously. A single global lock would serialize all operations, killing concurrency.

🎯 Why load FXML once?

FXML parsing is expensive. Loading both views at startup and caching the controllers means scene switching is instantaneous — just swapping which scene is on the stage.

🎯 Why daemon threads for simulators?

Simulator threads should not keep the app alive after the window is closed. Daemon threads are automatically killed when all non-daemon (UI) threads exit, preventing zombie background processes.

🎯 Why PropertyChangeSupport?

Java's built-in PropertyChangeSupport is a well-tested, named-event observer bus. Naming events (e.g. "vinylList", "selectedVinyl") lets consumers subscribe only to changes they care about.

🎯 Why deferred removal?

Removing a vinyl that's currently borrowed would cause a data integrity problem — someone holds it but the library doesn't know it exists. The flag ensures the vinyl stays tracked until it's physically returned.
