Web Accessibility Best Practices

Making the web usable for everyone

What is Web Accessibility?

Web accessibility means that websites, tools, and technologies are designed and developed so that people with disabilities can use them. More specifically, people can perceive, understand, navigate, and interact with the Web, and they can contribute to the Web.

Why Accessibility Matters:

  • 1 in 4 adults in the US has some type of disability (CDC)
  • Legal requirement: Many countries have laws requiring accessible websites (ADA, Section 508, European Accessibility Act)
  • Business impact: 71% of users with disabilities will leave a website that is difficult to use
  • SEO benefits: Accessible sites are better structured for search engines
  • Better UX for everyone: Accessibility improvements benefit all users, not just those with disabilities
  • Mobile-friendly: Many accessibility features improve mobile experience

Types of Disabilities to Consider:

Visual: Blindness, low vision, color blindness
Need: Screen readers, high contrast, scalable text
Auditory: Deafness, hard of hearing
Need: Captions, transcripts, visual indicators
Motor: Limited hand mobility, tremors
Need: Keyboard navigation, large click targets
Cognitive: Dyslexia, ADHD, autism
Need: Clear structure, simple language, consistent navigation

WCAG (Web Content Accessibility Guidelines):

WCAG is the international standard for web accessibility with three conformance levels:

  • Level A: Basic accessibility (minimum requirement)
  • Level AA: Addresses major barriers (most common target for compliance)
  • Level AAA: Highest level of accessibility (not always achievable for all content)

The Four WCAG Principles (POUR):

P - Perceivable: Information must be presentable to users in ways they can perceive
O - Operable: User interface components must be operable by all users
U - Understandable: Information and operation must be understandable
R - Robust: Content must be robust enough to work with current and future technologies
  • Semantic HTML
  • ARIA Labels
  • Accessible Forms
  • Keyboard Navigation
  • Color Contrast

1. Semantic HTML Elements

Why semantic HTML matters: Semantic elements convey meaning about the content they contain, not just how it looks. Screen readers, search engines, and other assistive technologies rely on semantic HTML to understand and navigate page structure.

Non-Semantic vs Semantic Example:

❌ Non-Semantic (Bad):
<div class="header">...</div>
<div class="navigation">...</div>

✓ Semantic (Good):
<header>...</header>
<nav>...</nav>

HTML5 Semantic Elements Explained:

<header> - Introductory content or navigation aids for a page or section
  Use for: Page headers, article headers, card headers

<nav> - A section containing navigation links
  Use for: Main navigation, table of contents, pagination

<main> - The dominant content of the document (only one per page)
  Use for: The primary content, excluding headers, footers, sidebars

<article> - Self-contained composition that could be distributed independently
  Use for: Blog posts, news articles, user comments, product cards

<section> - Thematic grouping of content, typically with a heading
  Use for: Chapters, tabbed content, grouped content areas

<aside> - Content tangentially related to surrounding content
  Use for: Sidebars, pull quotes, advertisements, related links

<footer> - Footer for a page or section
  Use for: Copyright info, contact info, related links, social media links

Proper Heading Hierarchy

Why heading hierarchy matters: Screen reader users often navigate pages by jumping between headings. A logical heading structure allows them to understand page organization and quickly find content.

Correct Heading Structure:
<h1>Main Page Title</h1> ← Only ONE h1 per page
  <h2>Section Heading</h2>
    <h3>Subsection</h3>
    <h3>Another Subsection</h3>
  <h2>Another Section</h2>
    <h3>Subsection</h3>

Incorrect (Don't skip levels!):
<h1>Page Title</h1>
  <h3>Skipped h2!</h3> ❌ BAD - Creates confusion
Best Practice: Use headings for structure, not styling. If you need smaller text, use CSS to style h2, don't jump to h4 just because it's smaller.

2. ARIA (Accessible Rich Internet Applications)

What is ARIA? ARIA is a set of attributes you can add to HTML elements to make web applications more accessible, especially dynamic content and advanced user interface controls developed with JavaScript.

⚠️ IMPORTANT - The First Rule of ARIA:
"If you can use a native HTML element or attribute with the semantics and behavior you require already built in, instead of re-purposing an element and adding an ARIA role, state or property to make it accessible, then do so."

Translation: Use semantic HTML first! Only use ARIA when HTML alone isn't enough.

ARIA Landmarks (Roles)

Landmarks define regions of a page, allowing screen reader users to quickly navigate to different sections. While HTML5 semantic elements have implicit roles, ARIA roles can be added for older browser support or to override defaults.

Landmark Roles:

<nav role="navigation" aria-label="Main navigation">
  Navigation links...
</nav>
/* role="navigation" is redundant with <nav> but OK for legacy support */

<main role="main">
  Primary content...
</main>

<aside role="complementary">
  Related content...
</aside>

<footer role="contentinfo">
  Footer content...
</footer>

<form role="search" aria-label="Site search">
  Search form...
</form>

ARIA Labels & Descriptions

Used to provide accessible names and descriptions to elements, especially when visible text isn't sufficient.

aria-label: Provides a label when there's no visible text
<button aria-label="Close dialog">✕</button>
/* Screen reader says "Close dialog button" instead of just "X button" */

aria-labelledby: References another element's text as the label
<h2 id="dialog-title">Confirm Delete</h2>
<div role="dialog" aria-labelledby="dialog-title">
  Dialog content...
</div>

aria-describedby: References descriptive text for additional context
<input type="password" aria-describedby="password-rules">
<div id="password-rules">Must be 8+ characters</div>

Live Regions for Dynamic Content

Why live regions matter: When content updates dynamically (via JavaScript), screen readers don't automatically announce the changes. Live regions tell assistive technologies to announce updates.

aria-live values:

aria-live="polite" - Announces when user is idle (most common)
<div aria-live="polite">
  Item added to cart
</div>

aria-live="assertive" - Interrupts user immediately (urgent messages)
<div aria-live="assertive" role="alert">
  Error: Form submission failed!
</div>

aria-live="off" - No announcements (default)

Specialized roles (shortcuts for aria-live):
role="alert" = aria-live="assertive" + aria-atomic="true"
role="status" = aria-live="polite" + aria-atomic="true"
✓ This is a live region that screen readers will announce when content changes

ARIA States & Properties

Common ARIA states:

aria-expanded - Whether element is expanded or collapsed
<button aria-expanded="false" aria-controls="menu">Menu</button>

aria-hidden - Hides element from screen readers
<div aria-hidden="true">Decorative content</div>

aria-disabled - Indicates element is disabled
<button aria-disabled="true">Submit</button>

aria-current - Indicates current item in a set
<a href="#" aria-current="page">Home</a>

aria-selected - Whether option is selected
<li role="option" aria-selected="true">Option 1</li>

4. Keyboard Navigation

Why keyboard accessibility is critical: Many users cannot use a mouse due to motor disabilities, visual impairments, or preference. Some rely on keyboard-only navigation, while others use assistive technologies that simulate keyboard input. Additionally, power users often prefer keyboard navigation for efficiency.

Who benefits from keyboard accessibility:
  • Users with motor disabilities who cannot use a mouse
  • Blind users using screen readers (which navigate via keyboard)
  • Users with tremors or limited hand mobility
  • Power users who prefer keyboard shortcuts
  • Users with broken or missing pointing devices

Essential Keyboard Commands:

  • Tab - Move forward through interactive elements (links, buttons, form fields)
  • Shift + Tab - Move backward through interactive elements
  • Enter - Activate links and buttons
  • Space - Activate buttons, check checkboxes, scroll page
  • Arrow Keys - Navigate within components (radio buttons, select dropdowns, sliders)
  • Esc - Close modals, dialogs, and menus
  • Home / End - Jump to first/last item in lists

Tab Order & Focus Management

Tab order is the sequence in which elements receive focus when pressing Tab. It should follow the logical reading order of the page (typically left-to-right, top-to-bottom).

Controlling tab order with tabindex:

tabindex="0" - Makes element focusable in natural tab order
<div tabindex="0">Now keyboard accessible</div>

tabindex="-1" - Focusable via JavaScript, not in tab order
<div tabindex="-1" id="modal-content">Modal</div>
/* Useful for modals - programmatically focus when opened */

tabindex="1+" - AVOID! Disrupts natural tab order
<input tabindex="3"> ❌ BAD - creates confusing tab order
/* CSS for focus states */
a:focus, button:focus, input:focus {
  outline: 3px solid #ff9800;
  outline-offset: 2px;
}

/* NEVER do this: */
:focus { outline: none; } /* ❌ BAD */

5. Color Contrast & Visual Design

Why color contrast matters: Sufficient contrast between text and background is essential for readability, especially for users with low vision, color blindness, or viewing in bright sunlight. Poor contrast affects approximately 1 in 12 men and 1 in 200 women with color vision deficiency.

WCAG 2.1 Contrast Requirements Explained:

Understanding Contrast Ratios:

Contrast ratio is a mathematical comparison between two colors, ranging from 1:1 (no contrast, same color) to 21:1 (maximum contrast, black on white or vice versa).

WCAG Level AA (Minimum - Most Common Target):
  • Normal text: 4.5:1 minimum ratio
  • Large text (18pt+ or 14pt+ bold): 3:1 minimum ratio
  • User interface components: 3:1 for boundaries and states
WCAG Level AAA (Enhanced):
  • Normal text: 7:1 minimum ratio
  • Large text: 4.5:1 minimum ratio

Note: Level AA is the legally required standard in most jurisdictions. Level AAA is recommended but not always achievable for all content types.

Common Contrast Mistakes:

❌ Common Failures:

• Gray text on gray background (#999 on #888) - 1.2:1 ratio
• Light blue on white (#64B5F6 on #FFFFFF) - 2.4:1 ratio
• Yellow on white (#FFEB3B on #FFFFFF) - 1.4:1 ratio
• Green "success" on white that's too light (#66BB6A on #FFF) - 2.8:1

✓ Good Examples:

• Black on white (#000000 on #FFFFFF) - 21:1 ratio (maximum)
• Your current scheme: #e0e0e0 on #121212 - 13.5:1 ratio ✓
• Dark blue on white (#0D47A1 on #FFFFFF) - 10.4:1 ratio
• White on dark green (#FFFFFF on #2E7D32) - 8.2:1 ratio
✓ Good Contrast
#e0e0e0 on #121212
Ratio: 13.5:1
✗ Poor Contrast
#666 on #555
Ratio: 1.2:1
Warning: Never rely on color alone to convey information. Use text, icons, or patterns as well.

7. Screen Reader Only Content

Sometimes you need text that's only for screen readers:

.sr-only {
  position: absolute;
  width: 1px;
  height: 1px;
  padding: 0;
  margin: -1px;
  overflow: hidden;
  clip: rect(0, 0, 0, 0);
  white-space: nowrap;
  border-width: 0;
}

The button above shows "✕" visually but screen readers hear "Close navigation menu"

8. Testing Your Accessibility

Manual Testing:

  • Navigate entire site using only keyboard
  • Test with screen readers (NVDA, JAWS, VoiceOver)
  • Increase text size to 200% - does layout still work?
  • Check color contrast with tools
  • Disable images - is content still understandable?

Automated Tools:

  • axe DevTools browser extension
  • WAVE (Web Accessibility Evaluation Tool)
  • Lighthouse in Chrome DevTools
  • Pa11y automated testing
